# TVBox 网页播放器可行性评估

日期：2026-10-29。状态：Web 首发、响应式与轻量后端、首版源兼容边界及搜索规则已确认；库选型与详细交互仍为建议。

## 已确认目标

- 电脑优先，手机方案需评估；用户关注桌面功能丰富度与维护复杂度。
- 首期只开发 Web；后续可能开发原生安卓 TV、Apple TV、macOS 与 iOS，尚无实施承诺。
- 首版面向个人/家庭，收藏与观看历史保存在当前浏览器，暂不做账号与跨设备同步。
- 已确认采用响应式 Web 与轻量后端；首版支持标准接口点播与 M3U 直播，不执行 Android Spider/JAR。
- 已确认同时支持站内搜索与用户主动发起的跨站搜索；结果保留站点归属，不自动合并同名影片。
- 同时提供点播、直播、订阅管理、内容排版、选集与视频播放。
- 换源同时包括切换播放线路与换站找片。
- 优先复用开源 UI 组件，考虑 shadcn/ui。
- 由开发方寻找并核验公开订阅样本。
- 本地 Markdown 管理任务，任务拆分经用户确认后发布。
- 已确认多订阅、单订阅浏览、手动更新；更新失败保留上一次成功数据。跨站搜索默认限定当前订阅的已支持站点。
- 已确认记忆进度、继续观看、可关闭的自动下一集；切线路优先匹配同名集数，不能确定时由用户选集。进度定位为尝试，不保证片源时间轴一致。
- 已确认播放失败保留选择，提供重试、切线路与换站入口，不自动跨站播放。
- 用户要求自有设计语言与规范，可参考 Apple TV 的高级感；具体方案见设计草案，尚待确认。

## 路线比较

| 路线 | 能力与限制 | 相对投入 | 判断 |
| --- | --- | --- | --- |
| 纯静态网页 | 能处理浏览器允许访问的配置、接口和媒体；受跨域、HTTP 混合内容及编码支持限制 | 初期低，源适配受限 | 可做有限功能版，不推荐作为当前目标的唯一方案 |
| 响应式前端与轻量后端 | 前端负责观看体验，后端统一获取配置及标准内容接口，必要时代理兼容媒体 | 中等；需维护一个服务 | 推荐；不承诺全量 TVBox 兼容 |
| 网页与 Spider 执行服务 | 需逐类处理脚本、Android JAR 依赖及其运行环境 | 高，运行隔离与长期维护成本明显增加 | 独立评估，不纳入首版承诺 |

后端代理能改变网络请求路径，不能自动获得 Android 运行环境，也不能自动解决 DRM、编码不支持、地域限制或来源失效。

## 手机端

建议同一应用、同一业务模型，电脑和手机分别组织页面布局。桌面保留多列海报、侧栏与视频旁选集；手机使用少列海报、抽屉筛选与视频下方选集。

响应式增加断点、触屏和横竖屏验证工作，但不要求删减桌面信息。独立手机站仍要做这些工作，并额外承担路由跳转、状态传递与两套页面维护；当前没有必须独立建站的证据。

播放器、选集、订阅和换源状态共享；只在结构确实不同的区域拆分桌面与手机组件。不把全部条件堆在单个页面中。

## 源兼容与证据

本次会话只读核验已获取 TVboxorg 聚合 JSON 与 iptv-org 中国频道 M3U；标准点播接口有返回数据的样本，但存在缺少 CORS 响应头与 HTTP 地址的问题。上述结果不构成实际播放通过。

- 订阅可读取：只能证明配置能获取和识别。
- 内容接口可读取：还需验证分类、搜索、详情与播放入口。
- 媒体可获取：仍需验证浏览器解码、持续播放与跳转。
- 实际可观看：须以明确设备、浏览器、网络和时间下的真实播放为证据。

首版建议支持经过样本验证的标准 CMS JSON 点播接口，以及 TVBox 配置内已验证结构的直播入口和 M3U 列表；不能仅凭 type 数字承诺兼容。依赖 Android JAR 的站点显示具体不支持原因，不假装导入后即可使用。

每个源记录核验时间、配置获取、内容接口和播放验证结果。以样本范围描述兼容能力，不写“支持所有 TVBox 源”。

## 开源组件与技术建议

- 前端候选：React、TypeScript、Vite，适合以交互为主且没有已确认 SEO 要求的播放器；尚未安装或锁定版本。
- UI 候选：shadcn/ui，复用按钮、对话框、抽屉、标签页、输入与反馈组件。其组件以源码进入项目，后续维护与升级仍是项目责任。
- 播放器候选：Video.js 等完整开源播放器；hls.js 是 HLS 播放能力库，不能单独替代完整播放器 UI。应先用真实样本验证候选，再锁定版本，不叠加两套播放器状态。
- 后端候选：Node.js 小型同源服务；可先在本机运行，再部署到能运行该服务的主机，不要求立即购买云服务。

技术选型目前是建议，不是实施授权。当前不安装依赖、不初始化业务代码。

## 页面组织建议

- 点播：分类与海报浏览、搜索、影片详情、播放与选集。
- 直播：当前视频与可搜索的频道分组；不把直播套进影片详情模型。
- 订阅：添加、更新、删除、切换订阅及查看兼容结果。
- 播放页突出当前影片、当前集与当前线路；跨站结果由用户确认，避免同名影片或集数不一致导致误播。

建议以低亮度蓝灰观看界面为视觉方向，让海报和视频承担主要色彩。shadcn/ui 提供基础交互，影片信息与选集组织保留业务定制；具体色板、字体和布局稿在产品边界确认后制定。

## 部署与持续成本

只代理配置和内容接口时，后端流量通常远低于代理全部视频；若媒体需要代理，出口带宽可能成为主要成本。按固定平均码率估算，5 Mbps 连续观看一小时约传输 2.25 GB，未计额外开销；这是计算示例，不是实测码率或报价。

建议兼容的媒体优先直连，需要代理时明确支持范围；若处理 HLS，不能只代理清单文件，还要核对分片、相对地址、密钥请求与 Range 行为。首版不做转码，避免增加算力和延迟成本。

引入任意订阅地址的后端需要限制目标协议、内网地址、重定向与请求规模，避免成为任意网络代理。首版已确定为个人/家庭使用；若后续面向公网多人开放，应另行确定身份、数据隔离和访问控制范围。

已确认首版观看历史与收藏保存在当前浏览器，不提供账号或跨设备同步。

## 后续原生端的影响

建议稳定订阅、站点、影片、播放线路、集数与频道的语义及外部数据转换边界，后续原生客户端可沿用数据协议。尚未决定后端必须由所有客户端共享，也不提前建立多端框架。

Web 组件与浏览器播放器不作为原生端可直接复用的承诺。电视焦点导航、遥控器操作、各平台播放器及系统能力在对应原生项目中单独设计。

本地观看历史以站点内的影片与集数身份记录，不假定不同站点的影片编号相同。将来同步需要单独设计用户身份与冲突处理，首版不预建账号系统。

## 实施前先验证

1. 点播选取一个真实标准接口，验证分类、搜索、详情、至少一集实际播放及切换集数。
2. 直播选取一个真实列表，验证分组、至少一个频道实际播放和切台。
3. 在目标电脑与手机浏览器验证播放控制、全屏、失败提示及布局。
4. 分别记录播放直连与代理路径的结果，再确定代理范围与部署资源。

未通过真实样本前，不以精美的模拟数据页面作为“源兼容已完成”的证据。真实浏览器验证需要用户授权，本轮尚未执行。
