# 后端源兼容扩展

日期：2026-10-30。状态：核心产品范围与单部署约束已确认；后端方案已完成源码调研，尚未批准实现任务。当前技术推荐与任务草案见 [后端方案调研](../research/2026-10-30-backend-recommendation.md)。

## 目标与事实基线

用户要求补齐后端能力，并指定通过 grill-with-docs 澄清、通过 to-tickets 拆分任务。首版完成状态仅对应当时确认的有限源兼容范围，不代表完整 TVBox 兼容。

以下依据当前源码静态核对；本轮额外读取了饭太硬公开订阅，未执行外部脚本、测试或浏览器验收。

| 层次 | 当前支持 | 尚未实现或限制 |
| --- | --- | --- |
| 订阅读取 | TVBox sites、MoonTV api_site、JSON 注释、已识别图片 Base64 包装 | 其他包装与加密格式没有通用适配；TVBox 订阅要求至少一个站点 |
| 点播站点 | type: 1 标准 CMS JSON；分类、分页、搜索、详情 | 非 type: 1 或带 jar 的站点被拒绝；XML、其他接口形状、脚本与 Spider/JAR 没有适配 |
| 播放入口 | HTTP(S) 且路径以 .m3u8 或 .mp4 结尾的点播直链 | 无扩展名媒体未探测；没有外部播放解析服务接入 |
| 直播 | 扩展 M3U 与 TVBox lives[type=0,url]，频道地址路径须以 .m3u8 结尾 | 专用请求头、其他列表结构和其他媒体格式未接通；EXTVLCOPT/KODIPROP 当前统一标记不支持 |
| 媒体传输 | 浏览器直连 | 后端没有媒体代理、HLS 清单改写、分片和密钥转发、MP4 Range 转发或转码链路 |
| 上游请求 | 公共 HTTP(S)、80/443 端口、逐跳及 DNS 地址校验、有界文本读取 | 不能按来源配置请求头；私网及非标准端口被拒绝；当前文本读取器不是媒体流式转发实现 |

源码入口：server/sources.js、server/live.js、server/remote.js、server/app.js、src/components/video-player.tsx。

## 已确认的目标修正

用户明确“最少，饭太硬也需要支持”，并指出当前协议不支持导致可看的剧很少。因此本轮以扩大真实可观看内容覆盖为目标，饭太硬为必须验收的订阅；不能仅导入配置、显示不支持，或用其他订阅的影片替代饭太硬结果。

此前建议将 Spider/JAR 相关站点一律推迟，不满足该目标，撤回。站点执行或等效服务端适配与播放解析必须纳入本轮方案；不能仅凭 type: 3 承诺普通 JVM 或 Node 可直接运行原工件。

用户进一步确认：饭太硬中的玩偶哥哥、盘搜等网盘资源纳入目标，需要在网页完成网盘登录并播放。网盘平台与登录方式须依据实际站点依赖核实；登录成功不能替代真实资源播放验收。

用户已确认每个网盘平台由家庭后端保存一份登录状态，电脑和手机共用；能访问该家庭服务的设备可使用已登录的网盘播放资源。页面提供状态、重新登录和退出入口。决定见 ../adr/0005-household-cloud-drive-login.md；凭据存储细节与登录方式由后续实际平台契约确定。

2026-10-30 从当前内置饭太硬入口重新读取：48 个站点全部为 type: 3，其中 45 个 csp_ 入口、3 个 drpy2 JavaScript 入口，另有顶层 spider 和 6 个直播入口。配置含网盘、普通影视、直播及其他内容入口，站点数不等于可播放影视站点数。记录见 ../development/fantaiying-compatibility-probe-2026-10-30.json；本次只证明配置结构，不证明运行器兼容或实际播放。

进一步静态读取当前 spider 工件：约 1.39MB 的 ZIP，MD5 与订阅声明一致，含 classes.dex、assets/ftyguard_v7.so 和 assets/ftyguard_v8.so，没有 .class 文件；Dex 可见 Android Context/Application 与 DexClassLoader 引用。现有 macOS arm64 主机可用 Java 17，但这不证明可以加载该工件。此证据要求先验证 Android/Dex 和原生依赖的兼容执行路径，不能安排成简单增加 JVM 服务。未执行工件或安装运行环境，记录见 ../development/fantaiying-spider-static-2026-10-30.json。

已核对本机具备 Android SDK、模拟器和 arm64 系统镜像；尚未启动或改动。用户随后明确不希望运行多个服务，因此撤回独立 Android 宿主作为优先方案。部署要求为一个后端部署单元、一个启动入口、一个对外端口。用户进一步要求充分研究包括 Java 迁移在内的方案，后端语言尚未确认；内部受应用管理的执行任务不直接等同于用户须维护多个服务。决定见 ../adr/0006-single-backend-compatibility.md。

## 待决策的范围

1. 单服务约束下饭太硬同站点适配的实际覆盖与平台依赖；网盘资源及家庭共享授权已确认纳入，磁力与专用播放能力仍需明确验收范围。
2. 选择真实站点和频道样本；以具体失败路径确定适配契约，不按格式名称宣称全部兼容。
3. 媒体代理的启用规则、请求头来源、部署带宽与并发目标。
4. 是否接入外部播放解析服务、是否需要转封装或转码，以及对应部署依赖。
5. 家庭局域网中的上游访问需求、设备和浏览器验收范围。

以上是决策树，不是已接受需求。后续问题根据已确认范围展开，不将所有候选能力默认纳入实现。

## 候选任务切片

最新拆分统一维护在 [后端方案调研的待评审任务](../research/2026-10-30-backend-recommendation.md)。它优先验证现成 Java 饭太硬兼容层，再接入主应用；不再预设只能逐站用 Node 重写。推荐结构是一个对外主应用自动管理内部 Java 执行器，有多个内部进程及回环代理，不需要用户另行管理 Android 或网盘服务；这属于待评审方案，不把用户的“单服务”直接解释成已经同意该实现。

尚未发布实现任务。第一项验证结束后据真实契约调整后续切片，不能以假定运行环境强行实施。

媒体识别、请求头与代理按上述真实观看路径落入对应任务，不单独交付只有接口而无可观看结果的“协议支持”。网盘登录与播放已纳入；是否需要转码或其他独立能力由真实样本和范围决定后再拆票。
